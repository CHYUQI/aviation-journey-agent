### [Heading 1] 第1章 引言
### [Heading 2] 1.1 软件设计目标和原则
本设计以课程汇报 PPT 所确定的“旅程伴随式 Agent”目标、docs/api/openapi.yaml 冻结契约和 aviation-journey-agent 当前代码为依据，给出可直接指导后续编码、联调和测试的软件实现说明。本文将 PPT 中的目标能力与截至 2026 年 9 月已经落地的能力分开表述，所有实现类名、属性和方法名均以代码为准。
当前版本已经形成完整的可运行闭环：Vue 创建表单提交行程，Gin REST 接口受理，DataAgent 通过 EOOB 航班检索、状态和机场信息技能补全世界状态，AdviceAgent 生成建议或安全降级，MemoryStore 保存快照，SSEHub 实时推送；前端同时提供定位/手动阶段确认以及断线轮询回退。嵌入式地图和实时道路导航 ETA 尚未实现，UML 对这些边界作明确标注。
设计过程遵循以下原则：
• 契约优先原则。docs/api/openapi.yaml 是接口路径、状态码、字段、枚举和空值语义的唯一真源；人读文档、前端生成类型和后端响应都必须与其一致。
• 关注点分离原则。DataAgent 只负责数据获取、标准化和质量判断；AdviceAgent 只消费 WorldState 并生成建议；前端只渲染，不进行风险、缓冲和阶段等业务计算。
• 高内聚、低耦合原则。API、Runtime、Agent、Skill、Store 和 SSE 各自承担单一职责，通过稳定接口协作，避免跨层直接访问内部状态。
• 安全降级原则。未知值用 null 表达，数组无内容时返回空数组；外部数据源失败不得拖垮整个分析，关键数据不足时风险必须为 unknown 或至少 yellow。
• 可解释原则。建议依据、数据来源、更新时间和降级原因通过 advice.reasons、state.quality 和 state.updatedAt 呈现，避免把辅助建议包装成确定承诺。
• 用户确认原则。导航、联系航司等动作由用户主动触发；系统不自动执行改签、支付、叫车等高影响操作。
• 迭代与可扩展原则。v1 先完成首个航段的可靠闭环，通过 Skill 接口扩展真实数据源，后续再扩展多航段、持久化和通知服务。

系统受 EOOB 可访问性、模型调用、网络质量和定位精度限制。当前 FlightIdentitySkill 负责按航班号与日期解析完整航段，FlightStatusSkill 调用 EOOB 结构化状态接口，AirportStatusSkill 解析 EOOB 机场页，RouteETASkill 依据机场坐标和旅客位置作直线距离×1.3、30 km/h 的低置信度估算。缺少可靠观测时字段保持 null 或 unknown。

### [Heading 2] 2.1 关键控制流程
创建行程时，JourneyHandler.Create 依次执行 ShouldBindJSON 和 CreateJourneyRequest.Validate，构造 Journey 后调用 Runtime.CreateJourney。Runtime 保存 Journey 与空 JourneyProgress，立即通过 publishProcessing 保存并广播 processing 快照，再由 analyzeAsync 启动最长 90 秒的后台分析；HTTP 层返回 202 AnalysisAccepted。
定位或手动阶段更新由 JourneyHandler.UpdateLocation 调用 Runtime.ApplyLocation。lat 与 lng 必须成对出现；坐标上报会清除旧 ManualStage，stage 上报会写入手动阶段。Runtime 同样先发布 processing，再异步执行 Recalculate。
Runtime 使用 sync.Map 字段 busy 对同一 journeyId 的并发分析去重。Recalculate 发现该行程正在分析时直接返回 Store 中的当前快照，不排队等待；不同 journeyId 仍可并行。该实现与“每行程互斥锁串行排队”不同，UML 按实际 busy.LoadOrStore 行为表示。
### [Heading 2] 2.2 数据与错误流
DataAgent 从 NewState 开始，通过 MissingFields 计算待查询字段，调用 Registry.Query 汇总各 Skill 的 Observation 和 issue，再由 applyObservations 做类型、枚举和 RFC3339 校验。单个 Skill 失败只追加 issue；只有 BuildState 返回错误时 Runtime 才生成 failed 快照。
HTTP 层参数错误返回 400，行程不存在返回 404，未预期服务端错误返回 500。分析过程错误不通过已结束的 POST 请求返回，而写入 status=failed 与 error。前端保留已有内容，显示错误横幅和重新分析入口。
### [Heading 2] 2.3 架构质量属性
• 可靠性：外部调用设置超时并支持部分成功；快照始终具有完整顶层结构。
• 实时性：位置变化完成重算后立即推送；无变化时每 15 秒发送 heartbeat。
• 一致性：/state 与 SSE snapshot 使用同一个 JourneySnapshot 类型，客户端不做增量合并。
• 可维护性：前端类型由 OpenAPI 自动生成；新增数据源通过实现 Skill 接口接入。
• 可测试性：规则计算保持纯函数；mockserver 提供正常、延误和失败场景。
• 安全性：只采集必要定位，不记录导航轨迹，不自动执行外部业务操作。

### [Heading 2] 3.3 界面可用性与异常设计
• 信息层级：风险、下一行动和关键时限优先，来源与解释可在下方查看。

• 无障碍：风险不能只靠颜色区分，必须同时显示文字；按钮具有明确标签和键盘焦点。

### [Heading 3] 4.1.1 “创建行程”用例实现的设计方案
JourneyHandler.Create 对请求体执行 ShouldBindJSON 和 CreateJourneyRequest.Validate。Validate 只检查 flights 非空以及每个 Flight 的 number、date、from、to 非空；IATA 正则和日期格式由 OpenAPI 契约描述，但当前 Go 校验尚未逐项执行。服务端使用 newJourneyID 生成不透明 ID，调用 Runtime.CreateJourney 后返回 202。
Runtime.CreateJourney 保存 Journey 与零值 JourneyProgress，通过 publishProcessing 生成并广播 processing 快照，然后由 analyzeAsync 调用 Recalculate。Recalculate 用 busy.LoadOrStore 去重，依次调用 data.Agent.BuildState 和 advice.Agent.Evaluate，最后由 finish 原子保存并通过 SSEHub.Publish 广播 ready 或 failed 快照。

### [Heading 3] 4.1.2 “更新位置或手动阶段”用例实现的设计方案
UpdateLocationRequest.Validate 要求 lat 与 lng 成对出现，并要求坐标或 stage 至少存在一种；stage 必须属于 ManualStages。JourneyHandler.UpdateLocation 调用 Runtime.ApplyLocation，行程不存在时返回 404。
ApplyLocation 读取现有 JourneyProgress：坐标存在时写入 Coordinate 并清除 ManualStage，stage 存在时再写入手动阶段。保存进度后立即发布 processing 并启动异步重算。RouteETASkill 按机场坐标计算 Haversine 直线距离，乘 1.3 路网系数并按 30 km/h 估算 ETA，结果标记为低置信度，不等同于实时地图路线。

### [Heading 3] 4.1.3 “查询状态与实时订阅”用例实现的设计方案
JourneyHandler.State 调用 Runtime.GetSnapshot 并返回 MemoryStore 中的完整快照，不在 GET 请求中触发分析。JourneyHandler.Stream 先 Subscribe、后 GetSnapshot，避免订阅与读取之间漏掉更新；随后写入 text/event-stream、no-cache、keep-alive、X-Accel-Buffering=no 和 retry: 5000。
Stream 建立后立即发送 snapshot，SSEHub 的后续更新继续发送 snapshot，15 秒无业务变化时发送 heartbeat。前端 createStream 监听 snapshot；浏览器自动重连，应用层在持续断开 20 秒后启动 15 秒轮询回退。

### [Heading 3] 4.2.1 DataAgent 详细设计
data.Agent 的输入 data.Input 包含 Journey 和 JourneyProgress。BuildState 先在航班身份不完整时调用 FlightIdentitySkill 解析航段，再由 data.MissingFields、skill.Registry.Query、applyObservations 和 assessQuality 构造结果，输出 data.Result{State, Journey, Issues}，使补全后的 Journey 同步进入快照。
skill.Observation 包含 Field、Value、Source、ObservedAt 和 Confidence。FlightIdentitySkill 调用 EOOB 航班搜索 JSON，FlightStatusSkill 调用 EOOB 状态 JSON，AirportStatusSkill 解析 EOOB 机场 HTML 及其中的客流/延误数据，RouteETASkill执行本地距离估算；前三者使用 5 分钟缓存或受控 HTTP Client，单项失败转化为 issue 而不伪造观测值。
### [Heading 3] 4.2.2 AdviceAgent 详细设计
advice.Agent.Evaluate 先调用私有 evaluate。模型未配置、输入构造失败、模型调用失败或枚举校验失败时，degraded 返回 risk=unknown 的空建议；手动阶段存在时覆盖模型返回的 Stage；最后由 enforceRiskFloor 执行代码级风险下限。
课程 PPT 提出的 bufferMin = latestDeparture - serverNow - etaMin 是目标规则，但当前代码尚未实现独立的确定性缓冲计算。当前 enforceRiskFloor 按 Stage 检查航班状态、时间轴和 ETA，关键数据缺失时把 Risk 设为 unknown，并过滤带 Nav 的行动，防止数据不足时给出高强度导航建议。
模型输出先进入 modelAdvice，再由 valid、toDomain 和 cleanStringPtr 做结构清洗。Action 的导航意图只允许模型写符号值 airport，实际 Nav 由 BuildAirportNav 根据机场 IATA 生成；无法识别机场时返回 nil。
### [Heading 3] 4.2.3 Runtime 与并发控制
Runtime 不维护每个行程的互斥锁队列，而用 sync.Map busy 标记正在分析的 journeyId。并发调用 Recalculate 时，首个调用执行分析，后续调用直接返回当前快照。finish 先 SaveSnapshot 再 Publish，使客户端只观察到完整快照。
StartPeriodicRefresh 每隔配置周期遍历 MemoryStore.ListJourneyIDs 并调用 Recalculate；服务关闭时 context 取消 ticker。SSEHub 只发布结果，不触发分析。位置或阶段更新由 ApplyLocation 单独触发，不等待周期刷新。

### [Heading 3] 4.4.1 部署安全与运维
• 生产环境必须通过 HTTPS 传输定位和航班信息，外部服务密钥只保存在服务端环境变量或安全配置中。
• 日志记录请求标识、journeyId、处理阶段和错误类型，但不得记录完整精确定位或任何密钥。
• 为外部数据源和模型调用配置独立超时；错误进入 quality/reasons，不能无限重试阻塞旅程。
部署到反向代理后应关闭 SSE 缓冲并设置足够长的读取超时；当前服务端已发送 X-Accel-Buffering=no，并每 15 秒输出 heartbeat。
MemoryStore 不支持多实例共享。当前课程版本保持单个后端实例；若扩容，需要先引入共享持久化与跨实例发布机制。

### [Heading 2] 4.7 设计决策与后续扩展
本版已经实现单个 Go 后端二进制、内存存储、双 Agent 编排、EOOB 数据技能、SSE、断线轮询回退和可交互 Vue GUI；前端仍通过独立 Vite 工程运行。设计选择优先保证可运行、可解释和安全降级的 Agent 闭环，不把尚未落地的分布式部署、嵌入式地图或实时道路 ETA 写成已实现。
• 多航段：扩展 State 为当前航段视图并增加衔接评估，但保持 flights[] 和快照整体推送原则。
• 持久化：以 Repository 接口替换 Memory Store，实现进程重启恢复和多实例共享。
• 通知：在明确授权、频率限制和审计后增加独立通知通道，不能复用 advice.alert 充当事件历史。
• 更细粒度溯源：如产品确需逐字段来源和置信度，应先走契约变更流程，避免在现有 reasons 中继续膨胀。
• 真实航司操作：必须新增身份、权限、用户二次确认、费用展示、幂等和审计层，不能直接由当前 Action 执行。

测试确认“页面创建行程→后端异步取数→EOOB 状态返回→完整快照渲染→SSE 更新→手动阶段重算”的前后端闭环可复现。当前测试环境未配置模型 API Key，因此 AdviceAgent 按设计返回 risk=unknown 与空行动列表，并显示“模型未配置”等降级原因；这不是接口或 UI 故障。
